# OPTIMA — Paso 11C.3 — Habilitaciones técnicas por empresa

- **Base exacta:** `375f03e4871dc022fecfd5dd58e5fd2a6466a566`, rama `aprender-sesiones-optima`, 11C.2 en Preview READY.
- **Qué incorpora:** PATCH `/api/plataforma-modulos` derivado del router existente `api/usuarios.ts`, catálogo de empresas con versión y panel de habilitación/suspensión/reactivación de un módulo por vez. Sin función nueva de Vercel.
- **NO activar aún:** la variable `OPTIMA_MODULES_CHANGES_ENABLED` debe permanecer AUSENTE o distinta de `true`. El script no configura esa variable ni crea usuario global. Preview y Production pueden compartir Base Maestra real.
- **Autoridad:** sesión Redis vigente + `leerAccesoPlataforma` comprobado contra USUARIOS y EMPRESAS, usuario plataforma exclusivo por ID. ADMIN cliente no tiene estas operaciones. No puede alterar la propia empresa OPTIMA.
- **Seguridad:** un solo módulo por petición, motivo obligatorio, versión SHA-256 del estado consultado, doble lectura antes del cambio, bloqueo Redis por empresa, comprobación posterior de Airtable y denegación ante campos/estados inconsistentes. El bloqueo evita concurrencia entre peticiones de ESTA API; no garantiza transacciones contra ediciones externas directas de Airtable.
- **Campo existente:** se modifica SOLO `EMPRESAS.MODULOS_CONTRATADOS`; `CORE` (`USUARIO`) es obligatorio, no comercial y se preserva; se reconocen alias antiguos como `CUENTAS CORRIENTES` / `CUENTAS_CORRIENTES` y `AJUSTES` / `CONFIGURACIÓN`. Se usan opciones ya existentes en Airtable con `typecast:false`. No crea campos, registros ni tablas.
- **Significado técnico:** `suspender` retira el módulo del listado técnico y `reactivar` lo agrega. Con el esquema actual NO se diferencia permanentemente un módulo suspendido de uno nunca habilitado ni se guarda un contrato comercial. La conservación del estado contractual separado se deberá resolver antes de habilitar gestiones comerciales reales.
- **Revocación:** Core vuelve a leer módulos desde Airtable por sesión en cada petición, de modo que un módulo suspendido deja de ser efectivo en los endpoints que ya aplican el Core. Los módulos heredados todavía no migrados íntegramente mantienen riesgos aparte (P0/P3). Reactivar restaura permisos preasignados que continúen vigentes.
- **Auditoría:** el motivo se exige, pero no se persiste todavía en un registro auditable permanente. El Paso 12 debe implantar auditoría antes de activar escrituras reales; nunca presentar esta fase como control comercial final.
- **Pruebas:** suites aisladas por mocks; no ejecutar PATCH sobre clientes reales desde Preview. Primero completar 11C.4 y Paso 12 o establecer un procedimiento de pruebas independiente con registros ficticios y autorización expresa.
- **Pendiente independiente:** `STOCK_INVENTARIO` no se modifica ni se considera resuelto.
